Multi-file workspaces — mockup v2

0 · The base: a tree and tabs decided in v1 review

  • Every screen in v2 starts from this layout. The tree lists the workspace; the tabs hold the files you've opened.
  • Tabs drop .pathogen and the badges. Other file types, when they come, show their extension (cities.csv).
  • Same name in two folders: both tabs get a quiet folder hint, gears · parts and gears · demos, only while both are open. This is VS Code's rule (state 2).
  • Assumption: the tree and the breadcrumb drop .pathogen too, for the same reason.
  • Telling libraries from programs without badges: state 3 compares three ways. Recommended: two icons, a page for programs and a box for libraries.
  • What the preview shows: a rule change. needs your sign-off The preview shows the program you open. While you edit a library, it keeps the last program you looked at, if that program imports the file (directly, or through another library). If it doesn't, the preview moves to one that does. This replaces v1's "always main" (Q3 b) and decision 16's pin. Screens A–C are three ways to pick a different program by hand.
State

A · Tabs in the preview, one per program exploration

  • Answers: how you switch between programs, and which programs an edit to a library affects.
  • One pill per program: the primary first, with a small star, then the others by path. Click one to show that program. The file in the editor doesn't change.
  • Editing a library: the preview keeps the last program you looked at. A dot marks each program that imports the file you're editing (state 3: kit is imported by main and try-sizes, not by the gears demo).
  • The pills look unlike the editor tabs on purpose, so two rows of tabs don't read as one thing.
  • Pros: familiar; one click; costs one 28px row; keeps today's minimap as the navigator.
  • Cons: names only. You can't see the other drawings, or that one of them broke, without clicking. Six or more programs overflow the pane (it would need a "more" menu).
  • Open: should a program with an error get a red mark on its pill? (Probably yes, as in B.)

B · A strip of live miniatures in place of the minimap recommended

  • Answers: seeing every program at once, switching with one click, and where the minimap's job goes.
  • A Programs strip is docked under the preview: one live miniature per program, the primary first with a small star. Click a miniature to show it large. The file in the editor doesn't change.
  • The navigator: when you zoom in, the shown program's miniature carries the viewport rectangle (state 3). Drag it to pan; click elsewhere on it to jump there, as today's minimap does. At Fit there is no rectangle. Clicking another miniature switches programs, and the view goes back to Fit.
  • Where it sits: along the bottom. Drawings are usually wider than tall, and with the tree open the preview is about 470px wide, so height is the cheaper side. Along the top it would fight the fullscreen button and the stale badge. Down one side it would take about 115px of those 470.
  • Updating (state 4): a program that imports the file you're editing keeps its last picture, dimmed, with a small spinner, until it recompiles.
  • Errors (states 5, 6): a red mark on the miniature, and the error dot on the files in the tree. Hover says what went wrong; a click shows the program large, stale, with the error panel over the editor.
  • Collapsed (state 8): one line of names. It still switches programs, but has no pictures and no navigator; the zoom pill and dragging still work.
  • Not the snapshot strip. The snapshots page has its own film strip: frozen past images, by date, on another page. The fullscreen tray (bottom-right) shows this visit's snapshots. The Programs strip is live, captioned with file names, and lives only in the workspace view. Its name says "Programs", not "film".
  • Fullscreen: the strip starts collapsed at the bottom-left. The zoom pill stays at the centre and the snapshot tray at the bottom-right, so they don't overlap.
  • What draws: you wrote "files with a define Viewbox(...) declaration". Recommended: every program draws, meaning every file without module;. A program without define ViewBox still draws, at the default 0 0 200 200 (state 7; the footer says "default"). That's the compiler's own test, so a quick try with no ViewBox still shows up. "Only programs that define a ViewBox" would hide drawings that work in the CLI and VS Code.
  • Performance: every miniature is a compile. Only the shown program compiles on each keystroke. The others recompile after a pause (about a second with no typing), only when a file they import changed, one at a time in the worker, and are cancelled if you type again. A miniature is drawn from its program's last result, scaled down as the minimap is today, so it costs no extra compile. Off-screen miniatures wait until they're scrolled into view.
  • Open: past four programs the strip scrolls sideways. Should a double-click on a miniature also open its file?

C · Choosing in the tree exploration

  • Answers: how to send a program to the preview from the tree, without a picture strip.
  • Recommended control: a dot. It is filled on the program that's shown. Hovering another program's row shows an empty ring, with "Show in preview" as its tooltip. The row menu has "Show in preview" too, in words.
  • Why a dot. Exactly one program is shown at a time, and a radio-like dot says "one of these". A pin says "stay put", which is no longer the job: the preview already follows you. An eye already means hide/show in the layers panel, and an eye says that several can be on at once.
  • The dot appears only on programs, so it is also a second way to tell them from libraries.
  • Pros: takes no space; it lives where the files already are; it works for any number of programs.
  • Cons: no pictures. It's hidden when the tree is closed, and on narrow screens (where the tree is a slide-over). A dot without a word needs its tooltip once.
  • Open: opening a program already shows it. So the dot is only for "show without opening". Is that worth a control on every row, or is the row menu enough?
State

D · Demos as files recommended: any program can be a demo

  • Answers: how a library gets a picture now that a library never draws.
  • A demo is just a program that imports the library. While you edit a library, the preview shows the last program you looked at that imports it; if none, the first program that does.
  • State 1: you open parts/labels. main doesn't import it, so the preview moves to the gears demo, and a label says why.
  • Conventions (state 2): a demos/ folder, a gears.demo name, or none. Recommended: none the tools depend on. The import is what ties a demo to its library. A demos/ folder is a good habit, and "New demo" in a library's row menu makes it free: it creates demos/<name> with the import filled in (states 3, 4).
  • A .demo name would be a new kind of file name, and it breaks "no extension shown means .pathogen".
  • The demo { } block (delayed) may not be needed. A demo file is a program like any other: you can open it, export it, or make it the primary. A block inside the library would be a second way to say the same thing.
  • Found along the way, not fixed: calling a fn on its own line inside a TextLayer's apply block fails with "Path commands cannot be used inside a TextLayer apply block", even when the fn only draws text. This happens in one file too. So parts/labels' caption() opens the 'captions' layer itself, and the program that calls it has to define that layer.
  • Open: should "New demo" add define ViewBox? It doesn't here: the demo draws at the default view box.

E · The primary program recommended

  • One program is the primary. Thumbnails, export, snapshots and publishing use it, as they use main today. pathogen.json's main stores it, so the CLI's folder mode agrees.
  • Chosen with "Set as primary" in a program's row menu, or in a miniature's menu (right-click) in the Programs strip.
  • Shown by a small star: in the strip (or the preview tabs), and, if you like, after its name in the tree. No pill, no badge.
  • A new workspace's first program is the primary. Deleting the primary asks which program takes over.
  • Open: Export and Snapshot while another program is shown. They use the primary; should their buttons say so ("Snapshot main"), or offer the shown program?
  • Open: one word. The UI says "primary", pathogen.json says main. Keep both, or rename the key?
