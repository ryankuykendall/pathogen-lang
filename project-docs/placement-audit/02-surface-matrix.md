## What the matrix says

### 1. Six operations silently change the value's kind

On a **ProjectedPath**, `subPath`, `union`, `difference`, `intersection`, `xor` and `cut`
all hand back a **PathBlock**. `src/pathogen-api.ts` declares every one of them as returning
a `ProjectedPath`, so completions, hover and chain-typing all promise the wrong thing.
ISSUE-025 records `subPath`; the other five are unrecorded.

The boolean ops and `cut` are the worse case, because the PathBlock they return still holds
**page numbers** — measured: `a.union(b).d` = `m 120 140 l -20 0 …` on paths projected at
(100,100) and (120,120). Drawing one re-offsets it from the cursor, double-placing it.

### 2. Six operations re-base; the rest keep the frame

| | re-based to `(0,0)` | keeps the receiver's frame |
|---|---|---|
| **PathBlock** | `reverse`, `subPath`, `segment`, `variableOffset` | `offset`, `outline`, `startAt`, `scale`, `mirror`, `rotate`, `fillet`, `chamfer`, `union`, `difference`, `intersection`, `xor`, `cut`, `dash`, `contours` |
| **ProjectedPath** | `subPath`, `toPathBlock` | everything else |

There is no principle separating the columns. It is decided one call at a time by a single
argument: `buildPathBlockFromCommands(cmds, origin?)` (`index.ts:1196`) subtracts
`cmds[0].start` when `origin` is **omitted** and subtracts nothing when it is passed
`{x:0, y:0}`. So `buildPathBlockFromCommands(cmds, { x: 0, y: 0 })` **preserves** the frame
— reading it as "put it at the origin" gets it exactly backwards. Nothing enforces a
convention; each new method picks one by hand.

### 3. The prior record of this matrix is stale

`project-docs/glyph-halo-diagnosis/STATUS.md:87` (2026-09-12) lists `offset()` in the
"re-origins at 0,0" column. Measured today, `offset()` **keeps** the frame
(`m 40 25 …` → `m 35 20 …`). That note is the only place this matrix has ever been written
down, and it drifted in twelve days. Hence `run-probes.sh`.

### 4. Recoverability — the axis that actually separates good from bad

For an operation that discards position, can the caller get it back **from the returned
value alone**?

| Operation | Discards? | Recoverable from the result? |
|---|---|---|
| `variableOffset` / `compoundVariableOffset` (block) | yes | **Yes** — `anchor` holds the removed translation |
| `toPathBlock` | yes | **Yes** — and the receiver is still in hand; documented as the point |
| `cut` pieces, dash pieces, `.contours` | no — carried as a leading `m` | Yes via `startPoint`, but correct only when drawn from `(0,0)` |
| `subPath` | yes | **No.** Nothing on the result knows. You need `receiver.get(t0)` |
| `segment` (block) | yes | **No** |
| `reverse` (block) | yes | **No** |

`variableOffset` is the only operation in the language that gets this right, and it only got
it right after the glyph-halo incident cost a day. `subPath`, `segment` and `reverse` throw
the position away with no way back.

### 5. Asymmetries between the two receivers

- **`drawTo` anchors different things.** PathBlock: the frame origin → `(x,y)`.
  ProjectedPath: the first inked point → `(x,y)`. `docs/path-blocks.md:95` states the
  ink version unconditionally.
- **Default pivots differ.** `rotate`/`scale`/`mirror` pivot on `(0,0)` for a PathBlock and
  on `startPoint` for a ProjectedPath.
- **Inside `@{ }`, every PathBlock method throws** (`index.ts:2790`) while **most
  ProjectedPath methods are allowed** (`:3447` blocks only `draw`/`drawTo`).
- **`point()`/`pointAll()` read different data**: authored records on a PathBlock,
  finalized commands on a ProjectedPath — so the same label can answer a pre-trim position
  on one receiver and a post-trim position on the other.
- **Missing members**, which force detours: `ProjectedPath` has no `project`, no `contours`,
  no `translate`; `PathBlock` has no `toPathBlock`; `TextBlock` has no `draw`;
  `ProjectedText` has no `toPathBlock`. The only way to translate a `ProjectedPath` is
  `drawTo` — which drops every label (`05-defects.md` D3).

## The text surface

Measured the same way (`text(0, 16)` inside `&{ }`, projected at `(100, 200)`):

| Operation | Result | `origin` |
|---|---|---|
| `TextBlock.project(100, 200)` | ProjectedText | `Point(100, 200)` |
| `ProjectedText.translate(10, 10)` | ProjectedText | `Point(110, 210)` — cumulative, correct |
| `ProjectedText.polarProject(0, 0, 0deg, 50, Center)` | ProjectedText | `Point(-57.52, -209.6)` — **a delta, not a position** |
| `TextBlock.boundingBox().width` | number | `15.04` |

`polarProject` on an already-projected value computes its anchor offset from absolute
element coordinates, so it stores an incremental delta and discards the prior origin — the
`-209.6` is the original `200` subtracted rather than replaced. Elements land correctly; a
subsequent `.drawTo()` does not. See `05-defects.md` D8.

**Not probed:** `TextBlock.toPathBlock()` requires a loaded font and the CLI cannot fetch
Google Fonts, so its placement is recorded from source only (`index.ts:4322-4389`: rebuilds
with an explicit `{x:0, y:0}`, i.e. the PathBlock's frame origin is the TextBlock's origin).
A probe would need a local TTF.

### Text asymmetries with the path surface

- **`TextBlock` has no `draw()`** — only `drawTo`. Text layers have no cursor, so there is no
  pen to draw at. PathBlock has both. This is defensible but undocumented as a rule.
- **`ProjectedText` has no `toPathBlock()`**, so the path escape hatch exists in one
  direction only.
- **`drawTo` anchors a third thing here.** PathBlock: the frame origin. ProjectedPath: the
  first inked point. ProjectedText: `origin`. Three definitions across four `draw*` entry
  points.
- **Three disagreeing width models** — `boundingBox()` uses a kerning-aware estimate,
  `toPathBlock()` sums per-character advance widths with no kerning, and the browser shapes
  the emitted `<text>` itself. None is guaranteed to agree with the others.
