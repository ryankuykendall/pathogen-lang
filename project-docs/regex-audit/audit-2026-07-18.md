# Compiler Regex-Reliance Audit — 2026-07-18

An audit of `src/` for risky over-reliance on regular expressions to parse
structured, grammar-shaped content — triggered by the CSS color regexes in
`src/color.ts` (`parseColor`). Three parallel exploration passes were run:
a regex inventory of `src/`, a map of the parser machinery and color/style
value flow, and a hunt for stringly-typed serialize→reparse round-trips.

**Headline:** ~30 regexes in `src/` parse grammar-like content. The color
regexes are real but are *not* the riskiest instance. The worst pattern is a
serialize→reparse round-trip on SVG path data in the core evaluator, and a
regex-based SVG sanitizer that is security-sensitive. A cross-cutting theme:
content the Lezer grammar deliberately captures as opaque blobs
(`CSSColorLiteral` interiors, `StyleContent`) is later re-parsed by regex
downstream.

**Architectural nuance on colors:** `oklch(0.7 0.1 200)` in Pathogen source
*is already tokenized* by the grammar as a `CSSColorLiteral`
(`pathogen.grammar:389-392`) — but with an unparsed `(![\)]*)` interior. The
AST builder produces `ColorLiteral{raw}` and the evaluator calls regex-based
`parseColor(raw)`. However, `Color("rgb(...)")` accepts **runtime strings**,
so a string-level color parser must exist no matter what the grammar does.
The right fix is therefore two-part: (a) replace the regex ladder with a
tokenizer built from atomic, individually-testable readers; (b) optionally
teach the grammar to structure color-literal interiors for compile-time
diagnostics (deferred — achievable with zero grammar risk by running the
string parser over `CSSColorLiteral` node text in `diagnostics.ts`).

## Stack-ranked findings

### Tier 1 — correctness/security-critical

**1. Path d-string serialize→reparse round-trip** —
`src/evaluator/segments.ts:329,339` (`NUMBER_REGEX`, `commandRegex`),
`src/evaluator/index.ts:1226` (`commandsToRelativeD`), draw/drawTo sites at
`index.ts:2420-2423, 2453-2457, 3175-3179`, `annotated.ts:574, 726, 5774`.

- The evaluator holds structured `PathBlockCommand[]`, serializes via
  `commandsToRelativeD()`, then immediately regex-reparses the string
  (`parseAndTrackPathString`) solely to reuse the cursor/context-tracking walk.
- Three near-duplicate regex tokenizers with **diverging number grammars**:
  `segments.ts:329` handles scientific notation; `annotated.ts:730` does not.
  `NUMBER_REGEX` (`-?[\d.]+`) mis-tokenizes implicit-decimal SVG forms
  (`1.5.5` = `1.5, .5` in SVG; regex yields `1.5` and silently drops data).
- The two `commandsToRelativeD` copies diverge materially: `index.ts:1226`
  is cursor-aware across `z`, supports `bridgeOriginGap`, formats via
  `formatNum`; `annotated.ts:574` uses naive `toFixed(4)`, no `z` cursor
  correction (plus inline `fmt` copies at `annotated.ts:1841, 1921`).
- No direct unit tests for the round-trip trio beyond 4 cases in
  `tests/segments.test.ts`.

**2. Regex-based SVG sanitizer** — `src/evaluator/svg-sanitize.ts:50-57,170,182`.
Parses user-supplied raw SVG with `TAG_RE`/`ATTR_RE` regexes and regex
`<defs>…</defs>` matching. Cannot correctly handle `>` inside attribute
values, comments, or CDATA — a sanitization-bypass surface, not just a
rendering bug (e.g. `<rect title="a>b" onclick="x"/>` truncates at the quoted
`>`). Deserves a cursor-based tokenizer and adversarial tests.

### Tier 2 — the flagged pattern (colors + style blocks)

**3. `parseColor` regex ladder** — `src/color.ts:485-565`. Nine anchored
regexes (rgb/rgba modern+legacy, hsl/hsla ×2, oklch, oklab, hwb, lab, lch),
each re-implementing number/percent/alpha sub-grammars. Known gaps vs CSS
Color L4: `none` components, scientific notation, `deg`/`turn` hue units,
`calc()`. Well tested behaviorally (`tests/color.test.ts`) but as a black
box — the sub-grammars aren't independently testable. The CSS-L4 percent
scalings (L/alpha 100%→1.0, chroma 100%→0.4, rgb 100%→255) must be preserved
exactly — the playground `hdr-color-input` picker round-trip depends on them.

**4. Style-block raw blob** — grammar `StyleContent { ![}]+ }`
(`pathogen.grammar:418`), scraped by
`/([a-zA-Z][a-zA-Z0-9-]*)\s*:\s*([^;\n]+);/g` in
`src/parser/ast-builder.ts:1864`, silent `catch {}` raw-string fallback in
`src/evaluator/index.ts:1391-1393`. The whole `${ … }` body is one token;
declarations are regex-split (a declaration missing its `;` is silently
dropped); each value is re-fed through the standalone Lezer expression parser
(`lezer-expression.ts`) with an invisible failure mode. Parsing declarations
as real grammar nodes yields per-property diagnostics, highlighting, and
positioned completions.

### Tier 3 — non-nesting `fn(args)` splitters

**5.** `src/parser/ast-builder.ts:1393` (`^(\w+)\(([^)]*)\)$`),
`src/evaluator/index.ts:1488` (`tryResolveCSSFunctionArgs`, greedy `(.+)`),
`src/evaluator/sanitize.ts:306, 360`. All fail or behave subtly on nested
parens / quoted `)` / commas inside args. `sanitize.ts:323` already has a
hand-written balanced `splitTopLevel` (near-duplicated as `splitCSSArgs` at
`index.ts:1464`) — extract into a shared tested utility.

### Tier 4 — language-services drift (IDE UX severity, not compiled-output)

**6. Regex source probes duplicating the AST** —
`type-inference.ts:127-296` (~20 dynamic regexes), `completion.ts:449-480`,
`semantic-tokens.ts:230`, `code-actions.ts:186-259`, `rename.ts:162`.
Reimplement declaration/scope resolution that the Lezer tree +
`scope-analysis.ts` already provide. Failure mode: false matches in
strings/comments, missed shadowing — degraded hints, not corrupt output.

**7. Self-string round-trips** — `diagnostics.ts:58,69` (regex-extracts
line/col from its *own* error message strings), `inlay-hints.ts:38,42`
(re-parses generated signature detail strings that `SIGNATURE_DATA` holds
structurally), `code-actions.ts:48` (`/^Undefined variable: (\w+)$/` on a
diagnostic message). Fix by carrying structured fields alongside the display
string.

### Tier 5 — minor / accepted

- `src/render/build-tree.ts:63` — `viewBox.split(/\s+/)` with no NaN guard.
- `src/cli.ts` font-path heuristics, XML-escape, kebab-case — trivial, no action.
- CSS relative-color expression *generators* (`color.ts:343-380`) are
  emit-only and never re-parsed — verified clean.
- `src/evaluator/code-snippet.ts` token table — presentation only.

## Remediation

Executed as a 6-phase plan (0: characterization tests; 1: shared
`path-data.ts` + round-trip elimination; 2: sanitizer rewrite; 3: tokenizer
`parseColor`; 4: grammar style declarations; 5: shared css-value utils +
language-services migration). Full plan preserved at
[remediation-plan.md](remediation-plan.md).

Key execution facts:
- Grammar regen: `npx @lezer/generator src/parser/pathogen.grammar
  --typeScript -o src/parser/pathogen.generated.ts`, then manually re-apply
  the `keyof typeof spec_Identifier` patch on the `specialized:` line
  (precedent commit `3fea81b`).
- Snapshot gate: `tests/render-snapshots.test.ts` must pass without
  `--update` through Phase 1.
- All phases are internal refactors (no `docs/` pages) except: Phase 2
  strictness changes if user-visible, and Phase 3's deferred CSS-L4
  extensions (`none`, exponents, `deg`/`turn`) which are user-facing and
  require docs-first + agentic review.
