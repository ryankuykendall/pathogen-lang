# Workspace Persistence Durability — Audit & Fix (2026-05-30)

## Verification status

- **Server: verified end-to-end** against the real dev API worker (`npm run
  dev:api`, actual HTTP + wrangler + local KV). Reproduced the incident: create
  `reddish` → save `yellowish` (baseRev 0 → rev 1) → stale save (baseRev 0)
  returns **HTTP 409**, and GET shows `code` is still `yellowish`. Thumbnail
  upload returns 200 and leaves `code` unchanged. Plus full handler unit tests.
- **Client: unit-tested only** (mocked `workspaceApi`/store), including the
  tricky paths (synchronous keepalive dispatch, `_baseRev` advance, 409
  surfaced on both normal and keepalive paths). NOT yet run in a real browser —
  the four browser-only behaviors below are left for a manual `dev:stack` pass.

## The incident

Workspace `experimenting-with-grids-2--4XsjQcS1b5Fe51eTOCbib`: the user changed
the primary color reddish → yellowish. The **thumbnail** captured yellowish, but
the **persisted code reverted to reddish**. Silent data loss.

The thumbnail is rendered **client-side** from the live preview SVG, so it always
reflects the newest editor state — its freshness proves nothing about what was
persisted. Multiple data-loss vectors produce the *exact same* end-state
(`code=reddish`, stale `updatedAt`, newer `thumbnailAt`). KV keeps no history, so
the specific incident is unprovable post-hoc.

> **Which vector hit this incident?** If the surviving thumbnail was auto/idle
> (5-min timer), the autosave would have persisted yellowish minutes earlier — so
> *something reverted it afterward*. That signature fits **multi-tab code-vs-code
> clobber** (a stale tab autosaving reddish after the good tab saved yellowish)
> at least as well as the server clobber. Field isolation alone does not close
> the multi-tab vector — so it is now also closed by **optimistic concurrency**
> (Vector 3 below).

Three vectors are fixed below: the server thumbnail clobber, the dropped unload
save, and the multi-tab code-vs-code clobber.

## Vector 1 — server-side clobber (fixed)

`uploadThumbnail` (`website/api/router.ts`) and `deleteThumbnail` read the whole
`workspace:${id}` doc and wrote it back just to stamp `thumbnailAt` /
`manualThumbnailAt` / `autoThumbnailAt` — dragging `workspace.code` along. Any
code write that landed between the handler's KV read and KV write was reverted.
The same shared-document read-modify-write also let a **stale second tab**
clobber a fresh tab's code.

**Fix: field isolation.** Timestamps moved to a sidecar KV key
(`thumbmeta:${id}`). Thumbnail endpoints write only the sidecar; code writers
(`updateWorkspace`, `createWorkspace`, copy) write only `workspace:${id}`. The
clobber is now impossible by construction.

- Helpers `readThumbMeta` / `writeThumbMeta` / `deleteThumbMeta` in
  `website/api/utils.ts`. `readThumbMeta` falls back to the legacy inline fields
  when no sidecar exists → **lazy migration**, no batch job. Existing workspaces
  migrate on their next thumbnail write.
- Prefix is `thumbmeta:` (deliberately **not** under `workspace:`) so
  `KV.list({ prefix: 'workspace:' })` scans (e.g. `adminListWithoutThumbnails`)
  don't mistake sidecars for workspace docs.
- Every read site that surfaces thumbnail timestamps now merges the sidecar:
  `getWorkspace`, `listWorkspaces`, admin approved/featured/rejected/flagged
  listings, the approval-record freeze, `publishApprovalToIndex`
  (`website/api/moderation.ts`), and the featured-cards SSR builder
  (`website/_worker.ts`). Card grids that read denormalized
  `PublicIndexEntry.thumbnailAt` are correct by construction.
- `deleteWorkspace` cascades a `deleteThumbMeta`.

## Vector 2 — dropped unload saves (fixed)

`apiRequest` (`playground/services/api.ts`) used a plain `fetch`, so a save fired
from the `beforeunload` handler was cancelled when the page tore down. With the
5s debounce + 30s min-interval, edits made shortly before leaving could never
land.

**Fix: keepalive flush + UX guards** (`playground/`):

- `autosave.saveNow({ keepalive })` dispatches `fetch(..., { keepalive: true })`
  on the unload path so the request survives teardown. **Subtlety (regression
  caught in review):** the keepalive fetch must be issued *synchronously* — any
  `await` before it (the SHA-256 dirty-check via `crypto.subtle`) defers the
  request to a microtask the browser won't run during teardown, so nothing gets
  sent. `saveNow`'s keepalive branch therefore skips the async hash, gates on the
  synchronous `hasUnsavedChanges()` signal, and fires immediately; the server's
  contentHash dirty-check drops any redundant write. Pinned by
  `tests/playground-autosave-keepalive.test.ts`.
- `beforeunload` shows the native "unsaved changes" prompt while a save is
  pending (`autosave.hasUnsavedChanges()`).
- Flush also on `visibilitychange → hidden` (reliable mobile/backgrounding
  signal) and on editor blur (`editor-blur` event from `code-editor-pane.ts`).
- Auto-thumbnail failures, previously `console.warn`-only, now raise a
  non-blocking `show-toast`. Code-save errors were already surfaced in the
  breadcrumb save-status pill.

## Tests

- `tests/api/workspace-thumbnail-no-clobber.test.ts` (new): workspace doc is
  byte-for-byte unchanged across an upload; the reddish→yellowish→thumbnail

- `tests/api/thumbnail-kind-split.test.ts` (updated): reads the sidecar instead

## Vector 3 — multi-tab code-vs-code clobber (fixed)

Two tabs open on the same workspace both autosave `code`; the slower (stale)
tab overwrites the faster tab's newer code. This is the vector that most likely
caused the reported incident (see the box at the top), and field isolation does
*not* close it.

**Fix: optimistic concurrency.** The workspace doc carries a monotonic `rev`
counter (`website/api/types.ts`), bumped on every accepted code write.

- `updateWorkspace` reads `baseRev` from the request body. When `code` is being
  written and `baseRev` is provided, it rejects with **409
  `{ conflict: true, currentRev }`** if `baseRev !== workspace.rev`. Accepted
  writes set `rev = currentRev + 1`. No-op saves (matching content) return
  `skipped` without bumping. Clients that omit `baseRev` keep last-write-wins
  (backward compatible). `createWorkspace` / `copyWorkspace` seed `rev: 0`.
- Client (`playground/services/autosave.ts`) tracks `_baseRev` (seeded from the
  loaded workspace via `autosave.init(id, hash, rev)`), sends it on every code
  save (normal + keepalive paths), and advances it from each response. On a 409
  it sets `_conflicted`, halts autosave (so it can't clobber or spin on doomed
  retries), surfaces the conflict (`workspace-conflict` event → existing
  multi-tab banner, plus a save-status message), and keeps `_pendingCode` so the
  edit isn't lost in memory. Reload re-inits at the latest `rev` and clears the
  flag.

### Review fixes folded in
- **Keepalive `_baseRev` sync (was a self-conflict bug).** The keepalive save
  bumps the server `rev`; on `visibilitychange` (page survives) the client must
  keep `_baseRev` in sync or the next edit after returning to the tab would
  falsely 409 and halt autosave. The keepalive branch now attaches a
  continuation that advances `_baseRev` (and handles a 409) when the promise
  resolves; on a true unload it simply never runs (reload re-seeds).
- **Non-code writes no longer clobber code.** Rename / preferences / publish
  updates write the whole doc, so a concurrent code save could be reverted via a
  different field. `updateWorkspace` now re-reads `code`/`contentHash`/`rev`
  immediately before the write when it didn't touch code itself, carrying the
  freshest values forward.
- **No-op (`skipped`) saves settle local dirty state** (`_pendingCode` cleared)
  so `hasUnsavedChanges()` doesn't keep firing the unload prompt; `saveNow`
  honors `_conflicted` so editor-blur/flush don't spin doomed 409s.

### Tests (concurrency)
- `tests/api/workspace-optimistic-concurrency.test.ts`: stale `baseRev` → 409 +
  newer code survives; sequential saves advance `rev`; no-op skip; omitted
  `baseRev` backward-compat; non-code updates don't require `baseRev` and
  preserve the latest code/rev.
- `tests/playground-autosave-concurrency.test.ts`: client sends/advances
  `baseRev`; keepalive save advances `_baseRev` when the page survives; 409
  halts autosave, surfaces conflict, retains the local edit; reload clears the
  conflicted state.

## Residual risk

The remaining gap is the **same sub-second window**: KV has no compare-and-swap,
so two code saves that both read `rev=N` before either writes can both write
`rev=N+1` and one still clobbers. For a single user this is exceedingly unlikely
given the autosave cadence (5s debounce + 30s min-interval per tab). Only a
per-workspace **Durable Object** (serializes all writes) or **D1** (real
transactions) closes it fully — a larger lift to hold in reserve if it ever
shows up in practice.

### Known limitation — keepalive 64 KB body cap

The Fetch spec caps `keepalive: true` request bodies at 64 KiB; a browser
silently drops a larger one. The unload save sends only `JSON.stringify({ code })`
(current `.pathogen` files top out ~22 KB, so there's headroom), but a very large
Grid()/data-driven workspace could exceed it. Backstop today: the `beforeunload`
"unsaved changes" prompt still fires (it doesn't depend on the fetch), so the
user is warned rather than losing work silently. If large workspaces become
common, add an explicit size warning before navigation, or chunk/compress the
unload payload.
