**Date:** 2026-03-16
**Scope:** Blog posts #11 (TextBlock Introduction) and #12 (Glyph Extraction)

## Post 1: TextBlock: Measure-First Text for SVG Diagrams

### Strengths

- **The compose-measure-position-draw lifecycle is clearly articulated and mirrors real interaction design workflows.** The post correctly establishes the parallel with PathBlock (the `&{}` / `@{}` sigil symmetry) and then builds up each lifecycle step progressively. Each section introduces exactly one capability, which is excellent pedagogy for an API introduction. The "Putting It Together" section at the end assembles the full pipeline in a single snippet with numbered comments -- this is the canonical reference pattern I'd expect from a well-designed tutorial.

- **The polar projection + BBoxAnchor section is the standout piece of API design communication.** The 9-anchor grid diagram, the convention that "the anchor faces the center," and the compass demo with 8 labels at 45-degree intervals make a concept that would otherwise require significant mental overhead feel immediately intuitive. The code snippet showing the loop with `names[i]` and `anchors[i]` in parallel is idiomatic and minimal -- no magic numbers, no per-label special-casing. This is the kind of example that developers will copy directly into their own work.

- **The collision avoidance section correctly frames the problem before presenting the solution.** The before/after demo (naive fixed-offset vs 8-angle search) is effective because both panels use the same data and the same visual language. The reader can scan left to right and immediately see the value. The 8-angle search code is well-commented and the greedy algorithm caveat is honest about the tradeoff: fast, not globally optimal, good for typical cluster sizes. This honesty builds trust.

- **Accurate technical claims about the measurement system.** The post correctly states ~85-90% accuracy for Latin text, which matches the implementation's per-character width tables in `src/evaluator/font-metrics.ts`. The three font categories (sans-serif, serif, monospace) match the actual `CHAR_WIDTHS_SANS`, `CHAR_WIDTHS_SERIF`, and `CHAR_WIDTH_MONO` tables. The bold ~6% increase matches `BOLD_WIDTH_FACTOR = 1.06`. The style properties listed (font-size, font-family, font-weight, letter-spacing, tspan dx/dy) all have corresponding handling in `estimateTextBoundingBox()`.

- **The `.intersects()` overloads are well-documented.** The post mentions three accepted types (ProjectedTextValue, ProjectedPathValue, plain `{x, y, width, height}` object) which matches the evaluator's actual implementation at the `case 'intersects':` handler. The collision avoidance demo exercises both text-vs-text and text-vs-rectangle checks (for dot positions), which demonstrates realistic multi-type usage.

### Weaknesses

- **The `<<` operator explanation arrives late and somewhat disjointed from the measurement discussion.** The first code example using `<<` appears in the "Measuring Before You Place" section (`let label = &{ text(0, 14)` + "`Hello World`" + ` } << ${ font-size: 14; };`) before the operator has been formally introduced. The "Style Merge with <<" section then backtracks to explain it. For a developer encountering this API for the first time, this creates a comprehension gap. The operator should either be introduced before measurement (since measurement depends on styles) or the measurement section should avoid using it and defer styled measurement to after the `<<` section.

- **The `.boundingBox()` return value semantics on TextBlockValue vs ProjectedTextValue are mentioned but not demonstrated.** The post says "On a TextBlockValue, the bbox is relative to the origin... On a ProjectedTextValue, the bbox reflects the absolute position." This is an important distinction for developers, but there is no code example comparing the two. A side-by-side showing `label.boundingBox()` returning `{x: 0, y: ...}` vs `label.project(100, 100).boundingBox()` returning `{x: 100, y: ...}` would make this concrete. Without it, a developer might incorrectly assume `.project()` does not affect the bbox.

- **The collision avoidance demo's code snippet in the blog does not perfectly match the actual sample source.** The blog shows a simplified loop with `let ok = true; for (prev in placed) { ... } if (ok) { best = candidate; found = true; }` but the actual `collision-avoidance.pathogen` sample has additional logic for checking against dot positions as rectangles and a `found == false` guard on the outer loop. While simplification for prose is reasonable, the gap between the "look at this code" presentation and the actual runnable demo could confuse readers who open the mini-workspace and try to reconcile the two. Either the blog snippet should include a comment like `// (dot-position checks omitted for brevity)` or the sample should be paired down to match.

- **No discussion of performance characteristics for the collision avoidance pattern.** The post calls AABB intersection "fast" and mentions it's "practical to run in a loop," but does not quantify or bound this. With N labels, the greedy 8-angle search is O(N^2) (each new label checks against all previously placed labels, and each check involves up to 8 candidates). For the 8-point demo this is trivial, but the post suggests this scales to "2-20 labels in close proximity" without noting that at 20 labels with 8 angles each, you're running ~1,600 intersection checks. For a parametric diagram that recompiles on every parameter change, this cost could become noticeable. A brief note about the quadratic growth and where it starts to matter would be valuable.

- **The coordinate model explanation could benefit from a visual.** The post explains that `text(0, 14)` places the baseline at y=14 and that "the text's visible pixels extend above that y coordinate, not below it." This is correct and mirrors SVG's `<text>` behavior, but it is a common source of confusion. A small inline diagram showing a text element with the baseline marked, the ascent above, and the descent below would prevent the misunderstanding that y=14 means the top of the text is at y=14.

### Overall Verdict

A strong introductory post that successfully communicates a well-designed API through progressive disclosure and high-quality interactive demos. The compose-measure-position-draw lifecycle is clearly taught, and the polar projection with BBoxAnchor is the highlight -- it turns a tedious manual task into a declarative one-liner. The main structural issue is the `<<` operator appearing in examples before being explained; reordering the sections would improve the first-read experience. The collision avoidance discussion would benefit from a brief performance caveat for larger label sets.

## Post 2: From Fonts to Paths: Glyph Extraction with PathBlock.fromGlyph()

### Strengths

- **The "text as geometry" framing is precise and immediately motivating.** The opening paragraph nails the distinction: TextBlock produces `<text>` elements rendered by the browser's font engine; `fromGlyph()` produces PathBlock geometry that participates in the full PathBlock pipeline (transforms, sampling, fillets, booleans). This is a real architectural distinction, not marketing language, and it correctly sets expectations for when each approach is appropriate.

- **The advance-width layout loop is taught incrementally and then reused across all subsequent sections.** The pattern (`cursor_x = 0; for g in glyphs { g.drawTo(cursor_x, baseline); cursor_x += g.advanceWidth; }`) appears in the manual layout section, is augmented in per-character transforms, and is used again in the text cutout pipeline. This repetition-with-variation is excellent for learning -- the reader internalizes the core loop and then sees how to extend it. The advance width accumulation matches the actual implementation: `(normalized as PathBlockValue & { advanceWidth: number }).advanceWidth = advanceWidth` in the evaluator.

- **The contour decomposition section is technically accurate and well-demonstrated.** The `.contours` property splits a glyph PathBlock using `splitContours()` in the evaluator, which is correctly described. The "Bingo!" decomposition counting 12 contours across 6 characters is a smart choice -- it exercises single-contour (n), double-contour (i, g, o, !), and triple-contour (B) glyphs in one example, showing that the feature handles the full range.

- **The per-character transforms section demonstrates genuine composability.** The wave, scale cascade, and circular arc examples each modify the advance-width loop in exactly one dimension. The blog correctly notes that `PathBlock transforms return new PathBlocks without modifying the original` -- this immutability is important for the scale cascade where `g.advanceWidth * s` uses the original advance width while the scaled glyph is a different value. The circular arc code using `.rotateAtVertexIndex(0, angle + PI/2)` matches the evaluator's implementation.

- **The "Paths vs Text" section honestly describes the measurement-rendering mismatch tradeoff.** The post correctly identifies that `fromGlyph()` eliminates the gap between measurement and rendering because both come from the same font file, while SVG `<text>` with estimation tables can diverge. The ~85-90% accuracy figure is repeated from Post 1 with appropriate context about when that gap matters (logo construction, stencil output) vs when it does not (label collision avoidance).

### Weaknesses

- **The text cutout demo does not actually use `.union()` and `.difference()` operations.** The blog's prose describes a three-stage pipeline: (1) extract glyphs, (2) `.union()` them into a single path, (3) `.difference()` to punch from a plate. The blog code snippets show `glyphs[0].project(x0, y).union(glyphs[1].project(x1, y))` and `plate.project(px, py).difference(text.project(tx, ty))`. However, the actual `text-cutout.pathogen` sample file uses a visual overlay technique instead: Stage 2 simply draws all glyphs to a single layer with solid fill (no `.union()` call), and Stage 3 draws the glyphs in the background color on top of a green rectangle (no `.difference()` call). The arrows between stages are labeled `.union()` and `.difference()`, but these operations are not invoked in the code. This is the most significant technical accuracy issue in either post. The demo visually approximates the result, but a reader who examines the source will discover that the advertised boolean pipeline is not actually exercised. Either the sample should be rewritten to use real `.union()` and `.difference()` calls, or the blog should clearly label it as a visual approximation.

- **The `@font` directive's environment-dependent behavior is described but not demonstrated in the mini-workspace context.** The post says the playground fetches from Google Fonts CDN, but the sample files use relative file paths (`"../../../../fonts/Bebas_Neue/BebasNeue-Regular.ttf"`). This means the demos work in the CLI compilation step but may require additional infrastructure to work in the playground's runtime environment. The post does not explain this discrepancy or describe what the reader should expect when trying these samples in the playground.

- **The `fromGlyph()` return type (array) is an unusual API choice that the post normalizes without questioning.** `PathBlock.fromGlyph("A", styles)` returns an array of one element, requiring `glyphs[0]` to access the single glyph. For single-character extraction this adds friction. The post implicitly accepts this by always showing `glyphs[0]` for single characters, but does not explain *why* the API returns an array even for one character (consistency with multi-character calls). A brief note acknowledging this design choice and its rationale would help developers who might otherwise wonder if they should use a different method for single characters.

- **The circular arc text code snippet in the blog uses `0.5pi` shorthand that differs from the actual sample.** The blog shows `g.rotateAtVertexIndex(0, calc(angle + 0.5pi))` while the actual `per-char-transforms.pathogen` file uses `calc(angle + 0.5 * 3.14159265358979)`. This raises the question of whether `0.5pi` is valid Pathogen syntax or a blog-only shorthand. If it is valid syntax, the sample should use it for consistency; if it is not, the blog should use the same explicit form as the sample. Either way, the mismatch between prose and demo source is a readability issue.

- **No performance discussion for glyph extraction at scale.** The post demonstrates `fromGlyph()` on short words (3-8 characters) but does not discuss what happens with longer strings. Each character requires font lookup, outline extraction, Bezier conversion, and PathBlock construction. For a parametric diagram that regenerates on every slider change, extracting glyphs for a full sentence on each recompile could introduce perceptible latency. A sentence noting that glyph extraction is a compile-time operation (not frame-rate sensitive) and that results can be cached via variables would reassure developers working on interactive content.

### Overall Verdict

A technically rich post that successfully bridges font engineering concepts (advance widths, contour decomposition) with the PathBlock composability model. The per-character transforms and the "text as geometry" narrative are compelling and well-demonstrated. The most significant issue is the text cutout demo: the prose describes and the arrows label `.union()` and `.difference()` operations, but the actual sample file uses visual overlay instead of boolean operations. This gap between documented and actual behavior needs to be resolved before publication, as it undermines the core technical claim of the section.
