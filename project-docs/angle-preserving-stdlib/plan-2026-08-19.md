# Angle-Preserving Stdlib Functions

## Context

`glyphFontColor.hueShift(randomRange(-0.5pi, 0.5pi))` produces no visible variation. Root cause (confirmed, not a randomRange bug): stdlib dispatch flattens every `AngleValue` argument to bare radians (`src/evaluator/index.ts:7489`) and never re-wraps the result, so `randomRange` returns a bare number in `[-1.57, 1.57]` which `.hueShift()` then interprets as **degrees** (`colorAngleDegrees`, `index.ts:533`) — a ±1.57° shift instead of ±90°. This is the pre-AngleValue lossy behavior (documented as fixed in `docs/color.md:174` — "angles now survive variables") re-emerging across the stdlib call boundary. It affects every value-passing stdlib function: `randomRange`, `lerp`, `clamp`, `min`, `max`, `map`, `hashRange`, `abs`, `normalizeAngle`.

**Fix (user-approved direction):** make those functions angle-transparent — when angle inputs flow into the relevant argument slots, the numeric result is re-wrapped as an `AngleValue`.

Out of scope: the separate percent/`lighten()` clamp-saturation issue (`20%` is erased to `0.2` at the literal — there is no PercentValue type; `lighten` adds an absolute OKLCH L delta clamped at 1.0). Optionally one docs sentence noting percent converts at the literal.

## Verified facts that shape the implementation

- Exactly **3 plain-stdlib invocation sites**: `src/evaluator/index.ts:7487-7491`, `src/evaluator/annotated.ts:5049-5053` (expression call), `annotated.ts:6061-6063` (bare call statement). The three **context-aware** unwrap sites (`index.ts:7471-7474`, `annotated.ts:5041`, `annotated.ts:6030`) stay unchanged — those functions (polarPoint, arcFromCenter, heading, …) consume angles into geometry; `heading()` is documented plain-radians (`docs/stdlib.md:303`).
- Arithmetic/comparison/unary-minus already handle `AngleValue` operands (`index.ts:1622-1648, 1692`); path args coerce via `toNumber` (`index.ts:7607`); template literals format angles (`index.ts:5623`); `.deg/.rad/.pi/.turns` members work (`index.ts:4249`). A stdlib result becoming an AngleValue is safe downstream.
- `docs/syntax.md:1265` explicitly promises angle-*computing* fns (`atan2` etc.) return plain radians — keep that true (angle-producing wrap is out of scope: silent behavior change + arbitrary unit tag).
- `tests/annotated.test.ts:434` pins `arc()` unwrapping its Angle arg — `arc` is not in the transparent set, so that test's behavior is unchanged (comment update only).
- No playground/VS Code source special-cases stdlib returns — fix rides through `npm run build`.

## Per-function contract (`src/stdlib/math.ts`)

**Angle-transparent** — result wrapped as AngleValue iff ≥1 *relevant* arg is an AngleValue; unit tag = first relevant AngleValue arg's unit:

| Function | Relevant args | Why |
|---|---|---|
| `abs` | `[0]` | magnitude of an angle is an angle |
| `min`, `max` | `'all'` | picks one of the inputs |
| `lerp(a,b,t)` | `[0,1]` | endpoints carry unit; `t` is a ratio |
| `clamp(v,min,max)` | `[0,1,2]` | all three share value space |
| `map(v,inMin,inMax,outMin,outMax)` | `[3,4]` | **output** range determines result space |
| `normalizeAngle` | `[0]` | angle in → angle out |
| `randomRange(min,max)` | `[0,1]` | the reported bug |
| `hashRange(n,min,max,seed?)` | `[1,2]` | deterministic randomRange |

**Unchanged:** angle-consuming (`sin cos tan sinh cosh tanh polarX polarY sign deg smoothstep bump easeIn/Out/InOut floor ceil round trunc` — rounding radians of a deg-tagged angle is unit-dependent nonsense, stays plain), angle-producing (`atan2 asin acos atan rad mpi` — documented plain-radians contract), angle-irrelevant (`exp log pow sqrt random hash01 noise …`), and all of `stdlib/path.ts` / `grid.ts` (non-number returns pass through untouched).

  abs: [0], min: 'all', max: 'all',

Unwraps each arg (`isAngleValue(v) ? v.radians : v`), calls `fn`; non-number results return as-is (PathSegments etc.); if `ANGLE_PRESERVING_ARGS[name]` exists and a relevant raw arg was an AngleValue (`'all'` → any arg; index list → in-range indices, robust to optional trailing params), return `angle(result, firstAngleArg.unit)`, else plain.

## Risks / behavior changes (documented in Step 1)
1. Template/log output changes where a transparent fn was fed angles: `${lerp(0deg, 90deg, 0.5)}` now prints `45deg`, not `0.7853981633974483`.
2. Degree-reading color methods reinterpret such results (the fix itself) — programs that pre-compensated (e.g. ×180/π) will change output.
3. Path/geometry numerics identical (all consumers go through `toNumber` → radians).
4. Mixed angle/plain variadic `min/max` compares radians vs raw numbers, same as today; unit = first angle arg's, documented in the helper.
