# Web Components + SEO Primer for Pathogen

## Purpose

Research primer exploring how search engines, social crawlers, and AI crawlers interact with Web Components — and how Pathogen's hybrid architecture (vanilla Web Components SPA + worker-rendered static pages) stacks up against best practices. This document audits the current state, maps the technical landscape, and identifies actionable improvements.

---

## 1. Where Pathogen Stands Today

Pathogen uses a split architecture: interactive features run as a vanilla Web Components SPA (Shadow DOM, History API routing, pub/sub state), while SEO-critical pages are served as static or worker-rendered HTML.

### What's Working Well

**Static HTML docs page** (`website/docs-static/index.html`). Generated by `scripts/build-docs.ts`, this is a 221KB fully self-contained HTML file — all content embedded, sidebar navigation with scroll spy, syntax-highlighted code blocks, no JS required for content visibility. This is the gold standard for SEO: content is in the initial HTML response.

**Worker-rendered explore and featured pages** (`website/_worker.js`). The Cloudflare Pages worker renders `/explore` and `/featured` as full HTML with:
- `<meta property="og:title">`, `og:description`, `og:url`, `og:type` tags
- `<link rel="canonical">` with full URLs rooted at `https://pedestal.design`
- `<meta name="description">` for search snippets
- Paginated card grids with workspace thumbnails, names, descriptions, and dates — all in the initial HTML

These SEO routes are matched *before* the SPA catch-all in the worker, ensuring crawlers always get full HTML.

**History API routing** (`playground/utils/router.js`). All routes use `history.pushState()` and `location.pathname` — no hash-based routing anywhere. Routes like `/pathogen/blog/my-post` are clean URLs that crawlers can follow. The base path `/pathogen` is consistent across all routes.

**Flash-prevention theme script**. An inline synchronous script runs before any CSS loads on both static and worker-rendered pages:
```javascript
(function(){
  var t = localStorage.getItem('pathogen-theme');
  if (t === 'light' || t === 'dark') {
    document.documentElement.setAttribute('data-theme', t);
    document.documentElement.setAttribute('data-active-theme', t);
  } else {
    document.documentElement.setAttribute('data-active-theme',
      window.matchMedia('(prefers-color-scheme:dark)').matches ? 'dark' : 'light');
  }
})();
```
This eliminates CLS from theme flicker by setting `data-theme` and `data-active-theme` attributes on `<html>` before the first paint. All three surfaces (static docs, worker pages, SPA) share the same `pathogen-theme` localStorage key.

**Real `<a href>` links in static pages**. The docs page sidebar uses standard anchor links (`<a class="sidebar-heading" href="#getting-started-your-first-path">`) for navigation. Crawlers can follow these to discover all content sections.

**Sitemap and robots.txt** (`scripts/build-website.ts`). Generated at build time:
- `robots.txt` allows `/pathogen/docs`, `/explore`, `/featured`, `/blog`; disallows `/api/`, `/workspace/`, `/preferences`, `/admin/`, `/storybook`
- `sitemap.xml` includes all static pages plus dynamically-discovered blog post URLs (read from `website/blog/*.md` at build time)
- Includes `Content-Signal: search=yes, ai-input=yes, ai-train=no` directive

### Gaps and Risks

**Blog content lives entirely in the SPA**. `scripts/build-blog.ts` converts markdown files from `website/blog/` into `playground/utils/blog-content.js` — a JavaScript module exporting `blogIndex` (metadata array) and `posts` (slug-to-HTML map). The `blog-view` and `blog-post-view` components render this content inside Shadow DOM. No static HTML blog page exists, so social crawlers (Facebook, Twitter/X, LinkedIn, Slack, Discord) and AI crawlers see nothing when they hit `/pathogen/blog` or `/pathogen/blog/my-post`. The sitemap lists blog URLs, but crawlers that follow them get the empty SPA shell.

**SPA landing page has no meaningful content before JS**. The playground's `index.html` is a 31-line shell: `<app-shell></app-shell>` plus stylesheet and script links. The worker does serve a separate `website/index.html` landing page (86 lines), but it's also minimal. Neither provides content that crawlers can index.

**No JSON-LD structured data on any page**. The docs page, explore page, featured page, and blog pages have no `<script type="application/ld+json">` markup. JSON-LD helps search engines understand content type (article, documentation, creative work) and display rich results.

**No `<meta name="robots">` or fine-grained crawler directives**. While `robots.txt` handles path-level blocking, individual pages don't carry `<meta name="robots">` tags for page-level control (e.g., `noindex` for paginated explore results, `noarchive` for frequently-updated content).

**`:not(:defined)` CSS not used**. All 32+ custom elements use `this.attachShadow({ mode: 'open' })` in their constructors. Before the element's JavaScript loads and the class is defined, custom elements render as empty inline elements. Without `:not(:defined)` CSS rules to reserve space, there's potential CLS when elements upgrade — especially on slower connections where JS takes longer to load.

## 2. How Search Engines See Web Components

### Google Web Rendering Service (WRS)

Google runs an **evergreen Chromium** instance (updates within weeks of Chrome stable releases) that executes JavaScript and renders pages. Shadow DOM is flattened into the accessibility tree, and content inside shadow roots is indexed.

However, rendering is not instant. Google's pipeline has two phases:

1. **Crawl queue** — Googlebot fetches the raw HTML. If the page is a JS-only shell, it gets queued for rendering.
2. **Render queue** — WRS executes JavaScript and captures the rendered DOM. This can be delayed by seconds to days depending on crawl budget and page priority.

Practical constraints:
- **~5-second timeout** for JavaScript execution. If your components take longer to define and render, content may be missed.
- **Stateless rendering** — no localStorage, no cookies, no service workers. The flash-prevention theme script's `localStorage.getItem()` returns `null` in WRS.
- **30-day resource cache** — external JS/CSS files are cached aggressively. Version-bust filenames if you need changes picked up quickly.
- **No user interaction** — `click`, `scroll`, `IntersectionObserver` callbacks that require viewport events won't fire.

**Bottom line:** Google *can* render Web Components with Shadow DOM, but it's slower, more fragile, and lower priority than indexing content that's already in the HTML response.

### Bing

Bing uses an **Edge/Chromium-based** renderer but is less aggressive about JavaScript rendering at scale. Microsoft's documentation recommends dynamic rendering (serving pre-rendered HTML to bots) for JS-heavy sites. In practice, Bing is less reliable at rendering Shadow DOM content than Google, particularly for sites with lower authority or crawl budget.

### Social Crawlers (Facebook, Twitter/X, LinkedIn, Slack, Discord)

**Zero JavaScript execution.** Social crawlers are simple HTTP fetchers that parse raw HTML for specific meta tags:

- **Facebook/Meta**: `og:title`, `og:description`, `og:image`, `og:url` — parsed from raw HTML response
- **Twitter/X**: `twitter:card`, `twitter:title`, `twitter:description`, `twitter:image` — falls back to OG tags
- **LinkedIn**: OG tags, plus some Schema.org support
- **Slack/Discord**: OG tags for unfurl previews

If these tags are inside Shadow DOM or generated by JavaScript, social crawlers will never see them. Pathogen's worker correctly places OG tags in the `<head>` of server-rendered pages — but blog posts served through the SPA shell have no OG tags visible to these crawlers.

### AI Crawlers (ChatGPT Browsing, Perplexity, Claude Web Search, etc.)

AI-powered search and browsing tools generally **do not execute JavaScript**. They fetch raw HTML and extract text content. This is a growing category:

- **GPTBot** (OpenAI): Fetches raw HTML, no JS rendering
- **PerplexityBot**: Same — raw HTML only
- **ClaudeBot** (Anthropic): Raw HTML fetcher
- **Google AI Overviews**: May benefit from Google's existing rendered cache, but structured data and clear HTML content improve extraction accuracy

For Pathogen, this means the static docs page is fully visible to AI crawlers, but blog content and SPA-rendered pages are invisible.

## 3. The Spectrum: Shadow DOM to Light DOM

Web Components exist on a spectrum from full encapsulation to none. Each point trades off SEO visibility, style isolation, and JavaScript dependency:

| Approach | SEO | Style Isolation | JS Required | Best For |
|----------|-----|-----------------|-------------|----------|
| **Shadow DOM (JS-created)** | Requires WRS rendering | Full — styles don't leak in or out | Yes | Interactive widgets, design system chrome |
| **Declarative Shadow DOM** | In initial HTML (if server-rendered) | Full | No (for initial render) | Components needing encapsulation + SSR |
| **Light DOM + slots** | Slotted content crawlable in raw HTML | Partial — shadow host styles apply | Yes (for behavior) | Content components with some encapsulation |
| **Light DOM only ("HTML Web Components")** | Fully crawlable | None — inherits page styles | Optional (progressive enhancement) | SEO-critical content, GitHub's model |

### Where Pathogen's Components Fall

All 32+ Pathogen custom elements use JS-created Shadow DOM (`this.attachShadow({ mode: 'open' })`). This is the right choice for the interactive playground (code editor, SVG preview, console, workspace management) where style isolation matters and SEO is irrelevant.

For content pages (blog, docs), the architecture correctly bypasses the SPA entirely: docs are pre-rendered static HTML, and explore/featured pages are worker-rendered. The gap is blog — it's currently rendered through Shadow DOM components (`blog-view`, `blog-post-view`) with no server-rendered alternative.

## 4. Patterns That Work

### HTML-First Web Components (Progressive Enhancement)

The approach championed by Jeremy Keith, used by GitHub (via their Catalyst library), and increasingly adopted across the industry:

1. Author complete, semantic HTML
2. Wrap in custom elements
3. Enhance with `connectedCallback()`
4. Content survives without JavaScript

```html
<!-- Content is fully visible before JS loads -->
<time-ago datetime="2026-02-28T12:00:00Z">
  February 28, 2026
</time-ago>

<script>
class TimeAgo extends HTMLElement {
  connectedCallback() {
    // Enhance: replace static text with relative time
    const date = new Date(this.getAttribute('datetime'));
    this.textContent = formatRelative(date);
  }
}
customElements.define('time-ago', TimeAgo);
</script>
```

No Shadow DOM needed. The custom element *enhances* existing content rather than *replacing* an empty shell.

### Declarative Shadow DOM

For components that need style encapsulation *and* server-rendered content, Declarative Shadow DOM (DSD) puts the shadow root in HTML:

```html
<my-card>
  <template shadowrootmode="open">
    <style>
      :host { display: block; border: 1px solid var(--border); }
      .title { font-weight: bold; }
    </style>
    <div class="title"><slot name="title"></slot></div>
    <slot></slot>
  </template>
  <span slot="title">My Title</span>
  <p>This content is in light DOM — crawlable in raw HTML.</p>
</my-card>
```

Browser support is now baseline: Chrome 90+, Firefox 123+, Safari 16.4+. The `<template shadowrootmode="open">` is parsed by the HTML parser itself — no JavaScript needed for the initial render.

**Caveat:** DSD requires server-side template expansion. For Pathogen, this would mean expanding custom elements in the worker or build scripts, similar to how `build-docs.ts` already generates full HTML.

### Slot-Based Content Projection

Keep crawlable text in light DOM, use `<slot>` to position it within Shadow DOM layout:

```html
<blog-card>
  <!-- Light DOM: crawlable by all crawlers -->
  <h2 slot="title">Understanding SVG Path Syntax</h2>
  <p slot="summary">A deep dive into the extended path language...</p>
  <time slot="date" datetime="2026-02-15">February 15, 2026</time>
</blog-card>
```

The Shadow DOM template uses `<slot name="title">` etc. to position these elements. Crawlers see the light DOM content; users see the styled layout.

### Progressive Hydration

Rather than loading and initializing all components on page load, hydrate interactive components on interaction, visibility, or idle:

```javascript
// Hydrate when element enters viewport
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      import('./heavy-component.js');
      observer.unobserve(entry.target);
    }
  });
});
observer.observe(document.querySelector('heavy-component'));
```

This reduces main thread blocking (improving INP) and avoids loading JavaScript for below-the-fold components. Pathogen's static docs page already benefits from this implicitly — the page works without JS, and the only component loaded is `<theme-toggle>`.

### `:not(:defined)` CSS

Reserve space for custom elements before they upgrade to prevent CLS:

```css
/* Before the element's JS loads, it's "not defined" */
app-shell:not(:defined) {
  display: block;
  min-height: 100vh;
}

blog-card:not(:defined) {
  display: block;
  min-height: 200px;
  background: var(--bg-secondary);
  border-radius: 8px;
}

/* Hide content that will be replaced by shadow DOM */
app-shell:not(:defined) > * {
  visibility: hidden;
}
```

The `:not(:defined)` pseudo-class matches custom elements whose class hasn't been registered via `customElements.define()` yet. Once the element upgrades, these rules stop matching and the component's own styles take over.

## 5. Technical SEO Checklist

Concrete requirements for any page that needs to be indexed:

### Meta Tags (Server-Rendered)

- [ ] `<title>` — unique, descriptive, 50-60 characters
- [ ] `<meta name="description">` — compelling summary, 150-160 characters
- [ ] `<link rel="canonical">` — absolute URL, one per page
- [ ] `<meta property="og:title">`, `og:description`, `og:image`, `og:url`, `og:type` — in `<head>`, not inside Shadow DOM
- [ ] `<meta name="twitter:card">`, `twitter:title`, `twitter:description` — for Twitter/X card previews

**Critical:** These tags must be in server-rendered HTML. Never generate them with JavaScript or place them inside shadow roots.

### Structured Data (JSON-LD)

- [ ] `<script type="application/ld+json">` in `<head>` or `<body>`, never in shadow roots
- [ ] Use appropriate Schema.org types: `TechArticle` for docs, `BlogPosting` for blog posts, `CollectionPage` for explore/featured
- [ ] Include `name`, `description`, `datePublished`, `author`, `url` at minimum
- [ ] Validate with Google's Rich Results Test

### Navigation and Links

- [ ] Real `<a href>` links in light DOM for all page-to-page navigation
- [ ] History API routing for indexable pages (no hash-based routing)
- [ ] Breadcrumbs with `<a href>` links and optional `BreadcrumbList` JSON-LD

### Sitemap and Crawl Directives

- [ ] XML sitemap at `/sitemap.xml` with all canonical URLs
- [ ] `robots.txt` referencing sitemap, allowing/disallowing appropriate paths
- [ ] `<meta name="robots">` for page-level directives where needed (noindex for pagination, admin pages)

### Core Web Vitals

- [ ] **LCP < 2.5s** — Largest Contentful Paint. Ensure hero content is in initial HTML, not JS-rendered.
- [ ] **CLS < 0.1** — Cumulative Layout Shift. Use `:not(:defined)` CSS, explicit dimensions on images/embeds, font `display: swap` or `display: optional`.
- [ ] **INP < 200ms** — Interaction to Next Paint. Avoid long tasks on main thread, defer non-critical JS.

### Verification

- [ ] Test with JavaScript disabled — all SEO-critical content should still be visible
- [ ] Validate social sharing with Facebook Sharing Debugger, Twitter Card Validator, LinkedIn Post Inspector
- [ ] Check Google Search Console for indexing issues, CWV data
- [ ] Use Lighthouse CI for automated performance/SEO audits

## 6. Real-World References

### GitHub — HTML-First, Light DOM, Tiny JS

GitHub is the most successful large-scale Web Components deployment on the web. Their approach:

- **Server-rendered HTML first**: Every page is fully functional without JavaScript. Rails renders complete HTML responses.
- **Light DOM custom elements**: Components like `<relative-time>`, `<auto-complete>`, `<details-dialog>` enhance existing HTML. No Shadow DOM.
- **Catalyst library**: A lightweight framework (~3KB) for defining custom elements with decorators for targets, actions, and controllers. Inspired by Stimulus.
- **Tiny JS payloads**: Individual element definitions are small (~1-5KB each). Loaded on demand, not bundled into a monolith.

**Why it works for them:** GitHub is a content-heavy site where SEO matters for public repos, issues, and docs. Server rendering + progressive enhancement means content is always accessible.

### YouTube — Heavy Web Components, Google's Own Infrastructure

YouTube uses Web Components extensively (originally Polymer, now Lit-based):

- **Shadow DOM everywhere**: Most UI is Shadow DOM components
- **Relies on Google's own WRS**: YouTube can afford this because Google's rendering infrastructure prioritizes its own properties
- **Not a model for most sites**: The approach works only because YouTube has effectively unlimited crawl budget and Google's rendering pipeline is optimized for its own properties

### Lit SSR — Framework-Level Declarative Shadow DOM

The Lit team has built server-side rendering support that outputs Declarative Shadow DOM:

- Server expands Lit templates to HTML with `<template shadowrootmode="open">`
- Client-side hydration reattaches event listeners without re-rendering
- Still experimental, but the most mature SSR solution for Shadow DOM components
- Requires a Node.js server or build step — would need adaptation for Cloudflare Workers

### Enhance — HTML-First Web Components on the Server

Enhance (by Begin/Architect) takes a radical HTML-first approach:

- Custom elements are defined as pure functions that return HTML strings
- The server expands `<my-element>` into full HTML at request time
- Zero JavaScript required for initial render
- Client-side JS can optionally enhance elements after load
- Uses light DOM by default — no Shadow DOM unless explicitly opted in

**Relevance to Pathogen:** The `build-docs.ts` approach is conceptually similar to Enhance — converting source content (markdown) into complete HTML at build time. Extending this pattern to blog posts would follow the same principle.

## 7. Recommendations for Pathogen

Ordered by impact and effort:

### Blog Static Page (High Impact, Moderate Effort)

Mirror the docs approach: `build-blog.ts` should generate `website/blog-static/` with full HTML for both the blog index and individual posts.

**What this solves:**
- Blog content becomes visible to social crawlers → link previews work on Twitter/X, LinkedIn, Slack, Discord
- Blog content becomes visible to AI crawlers → Pathogen blog posts appear in AI-powered search
- Blog posts get proper OG tags, canonical URLs, and descriptions in server-rendered HTML

**Implementation sketch:**
- Extend `build-blog.ts` to generate `website/blog-static/index.html` (blog index) and `website/blog-static/{slug}.html` (individual posts)
- Follow the same pattern as `build-docs.ts`: embedded styles, flash-prevention script, full content in HTML
- Add worker routes in `_worker.js` for `/blog` and `/blog/:slug` to serve the static files (before the SPA catch-all)
- Include per-post OG tags with post-specific titles, descriptions, and dates

### JSON-LD Structured Data (Medium Impact, Low Effort)

Add `<script type="application/ld+json">` to server-rendered pages:

**Docs page** — `TechArticle`:
```json
{
  "@context": "https://schema.org",
  "@type": "TechArticle",
  "name": "Pathogen Documentation",
  "description": "Documentation for Pathogen, a language that extends SVG path syntax",
  "url": "https://pedestal.design/pathogen/docs",
  "publisher": {
    "@type": "Organization",
    "name": "Pedestal Design"
  }
}
```

**Blog posts** — `BlogPosting`:
```json
{
  "@context": "https://schema.org",
  "@type": "BlogPosting",
  "headline": "...",
  "description": "...",
  "datePublished": "...",
  "url": "...",
  "author": { "@type": "Person", "name": "..." }
}
```

**Explore/Featured pages** — `CollectionPage`:
```json
{
  "@context": "https://schema.org",
  "@type": "CollectionPage",
  "name": "Explore Pathogen Workspaces",
  "description": "Browse community-created SVG path workspaces"
}
```

### `:not(:defined)` CSS (Low Impact, Low Effort)

Add to `playground/styles/theme.css` or a dedicated `styles/fouc.css`:

```css
app-shell:not(:defined) {
  display: block;
  min-height: 100vh;
  background: var(--bg-primary);
}

app-header:not(:defined) {
  display: block;
  height: 48px;
  background: var(--bg-secondary);
}
```

This prevents layout shift when custom elements upgrade from undefined (inline) to their defined display mode. Particularly visible on slower connections or when JS bundles are cache-missed.

### Landing Page SEO (Medium Impact, Moderate Effort)

The worker-rendered SPA shell (`_worker.js` catch-all) currently serves a minimal HTML page. Consider:

- Adding meaningful content to the initial HTML shell (tagline, feature list, CTA) that's visible before JS loads
- Or creating a dedicated worker-rendered landing page for `/pathogen/` with full marketing content, similar to how `/explore` and `/featured` are handled

### Social Sharing Validation (Low Effort, Ongoing)

Test all public URLs with:
- [Facebook Sharing Debugger](https://developers.facebook.com/tools/debug/) — validates OG tags, shows preview
- [Twitter Card Validator](https://cards-dev.twitter.com/validator) — validates Twitter Card markup
- [LinkedIn Post Inspector](https://www.linkedin.com/post-inspector/) — validates unfurl preview
- [Open Graph Debugger](https://opengraph.dev/) — general OG tag testing

Run these after any change to worker-rendered pages or meta tag generation.
